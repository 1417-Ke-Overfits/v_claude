# ML Challenge 2026: Business Entity Resolution — Methodology

**Team Name:** 1417 Ke Overfits
**Submission Date:** 2026-09-26

---

## 1. Executive Summary

We resolve business entities across three noisy, independent sources with a
classic, fully-offline **blocking → precision-first classifier** pipeline. All
24.2M records are canonicalised (accent-stripping, native-script→Latin
transliteration for 8 Indic scripts, order-invariant address parsing with
multi-country state normalisation); candidates are generated by an
**IDF-weighted top-N** scheme computed with batched sparse matrix multiplication
(94.5% blocking recall at ~0.66B pairs); and each candidate is scored by an
**XGBoost** model over 35 similarity/relative features, thresholded for the
precision-heavy **F₀.₅** metric. Held-out macro F₀.₅ = **0.9226** (counting
blocking misses as false negatives; **0.9423** when scoring only the candidate
set). The pipeline is country-agnostic and handles the unseen **France** test
country without any hard-coding.

## 2. Methodology

### 2.1 Problem Analysis (key EDA findings)

Measured directly on the provided data (details in `docs/02`–`04`):

- **Scale:** train S1 2.21M / S2 5.03M / S3 5.29M; test S1 1.73M / S2 4.89M /
  S3 5.08M. Naive all-pairs ≈ 2×10¹³ — blocking is mandatory.
- **Ground truth:** 94.4% of S1 entities have ≥1 match (5.6% singletons); avg
  3.67 matches; 85% of matched entities appear in *both* S2 and S3.
- **Source character:** S1 is clean and romanised; S2/S3 carry the noise —
  ~3.3% empty addresses, ~4% domain-form names, and **~12–15% names in native
  Indic scripts** (Devanagari, Kannada, Telugu, Tamil, Bengali, Gujarati,
  Malayalam, Gurmukhi).
- **Test adds France** (~15%: SARL/SAS/EURL/SCI, French regions) — unseen in
  training, so nothing may be hard-coded to {US, India}.
- **Noise taxonomy:** char scrambles/typos, added accents, legal-suffix drift,
  `&`/`+`/`and`, domain forms, appended phone numbers, occasional alias names;
  address reordering, literal `null` tokens, state variants (abbrev/full/native),
  house-number drift, city typos, abbreviations, landmarks.
- **Signal strength (110k true pairs):** address token overlap is the strongest
  anchor when present (only 4.5% of matches have zero overlap, ≈ the empty-address
  rate); char n-grams beat tokens on names (8.5% vs 14.7% zero-overlap). Union of
  name-token / street-number / address / n-gram signals reaches a **99.3% recall
  ceiling**.

### 2.2 Solution Strategy

**Approach Type:** Blocking + gradient-boosted-tree classifier (precision-first).
**Core Innovation:** (1) offline **script-aware normalisation** that bridges
romanised ↔ native-script Indian names; (2) **IDF-weighted top-N candidate
generation via sparse matrix multiplication**, which makes high-recall blocking
tractable at 2.2M×10M scale; (3) **relative / cross-source features** that judge a
candidate against its S1's other candidates; (4) honest **macro-F₀.₅ evaluation**
that counts blocking misses, so the reported score is the true end-to-end number.

Everything is offline and permissively licensed (no external data lookup).

## 3. Candidate Generation (Blocking)

- **Cleaning** (`normalize.py`): NFKC + accent strip; native-script→Latin
  transliteration (indic-transliteration, IAST); business-name canonicalisation
  (legal-suffix separation, domain/phone/ampersand handling); order-invariant
  address token bag with US/India/France state-region normalisation; street-number
  extraction. Both raw and canonical fields are kept.
- **Blocking keys:** `n2` (sorted first-2 name tokens), `sn` (street#+state),
  `nt`/`at` (name/address tokens, DF-pruned), and composite `ns` (name+state) /
  `nn` (name+street#). Document-frequency pruning removes non-discriminative
  generic tokens (e.g. "services", "center") that would otherwise explode block
  sizes.
- **Ranking:** for each S1, candidates are scored by the **summed IDF of shared
  kept keys** and the top-N are kept. IDF weighting is essential — a shared *rare*
  key is far more indicative than a shared common one.
- **Implementation:** built as two sparse matrices (S1×keys IDF-weighted, and
  S2S3×keys binary); `A_batch @ Bᵀ` in batches yields the shared-IDF scores,
  top-N by `argsort`. Runs the full corpus in minutes.
- **Result (train GT):** N=300 → **94.48% recall**, ~0.66B candidate pairs
  (~300/S1). N=1000 → 96.1% recall (but did not raise final F₀.₅ — the extra
  candidates are weak). Blocking candidate set for the submission is in
  `output/candidate_pairs.tsv`.

**How true matches are not lost:** multi-key union (name + address + composite)
covers complementary evidence, reaching a ~99% recall ceiling; DF pruning is
tuned to keep that ceiling while bounding volume; IDF ranking keeps the strong
candidates at the top.

## 4. Matching Model

**Features (35 total; `features.py`):**
- *Name:* token & char-trigram Jaccard; RapidFuzz ratio, Jaro-Winkler,
  token-sort, token-set, partial ratio; length ratio; prefix; exact-canonical.
- *Address:* token Jaccard, Levenshtein ratio, token-set ratio, street-number
  exactness, state match, present-flags, length ratio.
- *Context:* country match, native-script / domain / legal-suffix flags, source.
- *Relative / cross-source (computed per S1 over all its candidates):* name-Jaccard
  rank, is-top, margin to runner-up, best other-source name-Jaccard, cross-source
  "twin" agreement, candidate-count.

**Model type:** **XGBoost** (Apache-2.0, ≪8B params), `max_depth=8, eta=0.2,
300 rounds, scale_pos_weight = neg/pos`. Beat LightGBM (0.894) and a Logistic
baseline (0.830) in a held-out bake-off, confirming the signal is non-linear.

**Threshold selection:** swept on a realistic-base-rate (~1% positive) validation
split of held-out **entities**, maximising **macro F₀.₅** globally and per country
(US/India/France). The optimum is a high threshold (~0.99), reflecting the
precision-heavy metric. Submission uses threshold 0.99.

**Training data:** featurised candidate pairs from a sample of S1 entities;
negatives subsampled for training, full base rate retained for validation.

## 5. Results & Error Analysis

- **Held-out macro F₀.₅ (honest, blocking misses = FN):** **0.9226**
  (US 0.945, India 0.890). Precision 0.96, recall 0.85.
- **Held-out macro F₀.₅ (candidate-only recall):** **0.9423**.
- **Model behaviour:** gates on address presence, then address similarity, falling
  back to name fuzzy scores when the address is weak — matching the EDA.

**Common false negatives (missed matches):** native-script Indian names whose
phonetic romanisation diverges from the English spelling *and* whose address is
weak/empty; genuine alias names; ultra-short names. India is the harder country
(0.890 vs 0.945 US).

**Common false positives (wrong merges):** different businesses that share a name
core and an address token but are distinct — kept rare by the high threshold
(precision 0.96).

**Experiments (docs/12):** raising the candidate cap did *not* help F₀.₅ (the
bottleneck is confident matching of hard cases, not recall ceiling); relative /
cross-source features gave a small gain; the honest-vs-lenient gap (~0.02) is the
"blocking tax".

---

## 6. Conclusion

A disciplined, fully-offline blocking→classifier pipeline — with script-aware
normalisation, IDF-weighted sparse-matmul candidate generation, and a
precision-first XGBoost tuned for F₀.₅ — resolves these noisy multi-source
business entities at scale, reaching a held-out macro F₀.₅ of 0.9226 (0.9423 on
the candidate set). The largest remaining opportunity is confident matching of
native-script / alias cases (India), addressable with stronger name features and
true pairwise cross-source corroboration.
